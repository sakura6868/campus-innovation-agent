# RAG 混合检索架构与赛事隔离机制

> 本文档**诚实标注**本系统的检索实现，可作为参赛文档中「技术创新点」的引用依据。

## 1. 一句话定位

本系统的检索并非「一个向量库查全部」，而是 **以赛事为单位做物理隔离 + 三层信号融合的混合检索**：每个赛事拥有独立的检索空间，跨赛事永不串味；查询时融合「语义向量余弦 + 关键词重叠 + 结构化字段精确匹配」三重信号，在零联网、零外部服务的前提下获得可解释、可追溯的官方依据。

## 2. 为什么需要「赛事隔离」

普通的 RAG 把全部文档塞进同一个向量库，靠 top-k 相似度取片段。在**高校竞赛导航**场景下这会引出两个真实痛点：

1. **跨赛事污染**：用户问「蓝桥杯的报名截止时间」，若语料里「互联网+」的截止时间向量更近，就会把错误赛事的字段答出来。
2. **年份/版本混淆**：同一赛事不同届次规则不同，混库检索会返回旧届次证据。

本系统把每个 `competition_id` 作为**硬隔离边界**（可选 Chroma 下每个赛事一个独立 collection + metadata 三重过滤；默认本地检索下直接按 competition_id 切片），从架构层面根除上述问题。这是本项目的**核心创新点之一**。

## 3. 三层混合检索信号

| 层 | 机制 | 作用 | 权重 |
| --- | --- | --- | --- |
| ① 语义向量 | `all-MiniLM-L6-v2`（384 维，离线打包 ~88MB）句向量余弦 | 命中 paraphrase，如「组队几个人」≈「团队人数要求」 | 0.8 |
| ② 关键词重叠 | 字符/分词重叠度（lexical） | 兜底精确术语召回，如「身份证」「学生证」 | 0.2 |
| ③ 结构化字段 | 报名截止 / 专业限制 / 年级 / 奖项 等字段级精确匹配 | 强约束事实（时间、资格）零歧义直取 | 作为独立高优块 |

最终排序 = `0.8 × 语义余弦 + 0.2 × 关键词重叠`，块向量按 `competition_id` 缓存到内存（数据静态时复用，避免重复编码）。

> **诚实标注**：默认路径（无远程 Chroma）下，向量检索在进程内对 DB 片段做余弦排序，**不依赖 Chroma 服务**——既绕开了受限环境下 Chroma 持久化的磁盘段错误，又拿到了真正的语义召回。Chroma 仅作为「接入外部大规模向量库」的可选增强，而非必需组件。

## 4. 默认即「真·语义检索」（离线零联网）

- 当 `all-MiniLM-L6-v2` 已离线预热到本地 HF 缓存时，**RAG 默认即为真实语义向量检索**，无需任何环境变量、无需联网。
- 环境变量开关（向后兼容）：
  - `RAG_USE_ST=0` → 强制关闭，退回轻量哈希向量 + 关键词（极小体积、极快启动）。
  - `RAG_USE_ST=1` → 强制开启真实 embedding。
  - 不设 → **本地有模型即自动开启**，缺失模型时优雅降级到轻量向量 + 关键词，保证服务零外部依赖可启动。
- 加载模型时若检测到本地缓存，自动置 `HF_HUB_OFFLINE=1`，规避受限网络下连 huggingface.co 超时卡死。

## 5. 可解释与可追溯（引用门控）

每条召回片段都携带完整 `Citation`：来源字段、官方文档名、官方链接、获取日期、最后核验时间、可信等级。Agent 引用门控会在「证据不足 / 字段无对应证据」时**主动拒答或提示人工复核**，而非编造——这比「能编出答案的 AI」更可信，是第二个创新点。

## 6. 与 naive RAG 的对比（可用于答辩）

| 维度 | 朴素 RAG | 本系统 |
| --- | --- | --- |
| 跨赛事隔离 | 无，易串味 | 按 competition_id 硬隔离 |
| 语义泛化 | 依赖单一向量库 | 语义 + 关键词 + 字段三层融合 |
| 外部依赖 | 常需向量库 + GPU | 零联网、零 Chroma 可跑 |
| 可追溯 | 片段难定位来源 | 每条带官方 Citation |
| 不确定处理 | 常硬答 | 门控拒答 / 提示复核 |

## 7. 部署建议

- **本地 / 比赛演示**：直接依赖离线 MiniLM，开箱即语义检索，最稳。
- **生产大规模语料**：设 `CHROMA_HOST` 接入远程 Chroma，每个赛事仍保持独立 collection，检索逻辑不变。
- **可选 LLM 润色**：设 `AGENT_LLM_API_KEY` 可在门控 + 检索结果之上做自然语言组织（默认空则用确定性模板，保证可复现）。
