## 一、验证思路

本项目按三类材料组织验证，其中第三类尚待实际开展：

1. **系统实测数据**：校验缺证据、多版本、截止边界等系统行为；不能单独证明学生需求或实际收益。
2. **真实迭代记录**：开发过程中反复试用发现并修复的问题，全部留存在公开 git 历史中，可逐条核验。
3. **试用记录**：团队试用 + 外部同学试用（见第三、四节）。

## 二、真实迭代证据（来自公开 git 历史，53 次提交中 19 次为修复类）

以下问题均是在**真实使用 / 部署 / 测试中暴露**后修复的，每条均可通过 commit hash 查验：

| # | 暴露的问题 | 使用中的表现 | 修复提交 |

## 五、答辩时怎么讲（话术建议）

> 2026-10-03 更正：下方旧话术的数据规模、提交次数等不是当前指标。公开信息缺口和代码迭代不能证明需求真实性；没有真实试用记录时直接说明尚未试点，不使用“已证明用户收益”等表述。最新口径见参赛验收矩阵及量化评测报告。

**避免说**：「我们调研了很多同学，大家都觉得很有用。」（无证据，易被追问）

**尚未试点时的建议口径**：

> 我们针对竞赛信息难以追溯和计划执行脱节设计了这套系统，目前完成了限定范围的官方证据核对、自动化回归和本地浏览器验收。公开数据中的缺口只是选题线索，不能证明学生确实因此受困。真实学生试用尚未完成，接下来会按匿名任务、完成耗时、成功率与失败记录验证需求及收益。当前评测成绩描述的是固定用例上的规则表现，不是满意度或实际推广效果。

**如果被问「有没有真实用户」**：
- 有外部试用 → 如实说人数和发现的问题；
- 还没有 → **直接承认**，说明限定的工程验证范围与推广计划，不用数据规模或提交次数替代真实需求证据。
