# 验证与迭代记录

> 对应命题五评审关注：**需求真实性**、**选题价值**。
> 本文件全部内容**可核验**：系统数据可复现、git 记录可查、数字均来自仓库真实提交。
> 指导思想与本项目一致的「不编造、来源可追溯」——**不以虚构问卷或假用户反馈充数**。

---

## 一、验证思路

本项目不以问卷自述作为唯一需求依据，而是三条真实证据链并行：

1. **系统实测数据**：用系统跑出的真实数据反证痛点客观存在（见《参赛作品说明》「需求依据」）。
2. **真实迭代记录**：开发过程中反复试用发现并修复的问题，全部留存在公开 git 历史中，可逐条核验。
3. **试用记录**：团队试用 + 外部同学试用（见第三、四节）。

---

## 二、真实迭代证据（来自公开 git 历史，53 次提交中 19 次为修复类）

以下问题均是在**真实使用 / 部署 / 测试中暴露**后修复的，每条均可通过 commit hash 查验：

| # | 暴露的问题 | 使用中的表现 | 修复提交 |
|---|---|---|---|
| 1 | 「智能车怎么备赛」**路由锁不住** | 用户按口语提问，系统返回不相关赛事 | `fc233fd` |

| 7 | 蓝图同步覆盖密钥 → **LLM 配置不生效** | 控制台配好的 key 被覆盖为空 | `558c6d0` |

| 11 | Chroma / Postgres URL **兼容问题** | 云端部署启动失败 | `c5b7173` |

## 四、外部同学试用（建议赛前完成）

> 📋 直接可用的**真人试用记录表 + 操作指引 + 复跑脚本**已单独抽到 `docs/TRIAL_FORM.md`。
> 关键原则：表的「用户评价」栏**必须由真人本人填写**，开发者只能用 `scripts/trial_replay.py` 把真人提问复跑出**系统客观输出**作佐证，不得代写评价。

**这是当前性价比最高的补分动作**（落地价值 30 分中约 5 分）。建议做法：

## 五、答辩时怎么讲（话术建议）

**避免说**：「我们调研了很多同学，大家都觉得很有用。」（无证据，易被追问）

**建议这样说**：

> 需求真实性我们用三层证据来保证：
> 第一，系统数据本身——190 条赛事里 36 条找不到可核验官方来源，我们如实标记而不是猜，这说明信息不可信是客观存在的；
> 第二，真实迭代——仓库 53 次提交里 19 次是修复，其中像「依赖缺失导致线上静默失效」这类问题，只有真正部署才会暴露；
> 第三，真实试用——（如有）我们请了 X 位同学实际使用，发现了 Y 问题并已修复。
> 另外所有数字评委都可以现场复现核验。

**如果被问「有没有真实用户」**：
- 有外部试用 → 如实说人数和发现的问题；
- 还没有 → **直接承认**，然后强调前两层证据 + 说明推广计划（见《参赛作品说明》第十一节）。诚实比圆谎安全，且评委会认可"知道自己边界"的工程态度。
